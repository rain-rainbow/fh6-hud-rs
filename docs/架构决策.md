# 架构决策记录

本文件记录**为什么这样设计**，以及每条结论的**实测依据**。
格式沿用 ADR（Architecture Decision Record）风格：结论 + 理由 + 证据。

---

## ADR-001：语言选 Rust 而不是 C

**结论**：用 Rust，目标三元组 `x86_64-pc-windows-gnu`。

**理由**：需求是「降低对机器的资源和性能占用」。而**资源占用的瓶颈不在语言**：

* 遥测收包 + 解析是 60 Hz、324 字节/包 ≈ 19 KB/s。这个量级用 Rust 还是 C
  都是测不出来的差别（都 <0.1% CPU）。
* 真正的开销来自 **GUI 与窗口合成**：Electron（几百 MB 内存 + 独立
  Chromium）、Python + PyQt6（CPU 软件光栅化 + 全屏每帧重绘）、WPF（.NET 运行时）。

所以正确做法是「原生编译 + 轻量渲染 + 分层窗口」，而不是纠结 Rust/C。

选 Rust 而非 C 的具体理由：

| 维度 | Rust | C |
|---|---|---|
| 内存安全 | 编译期保证 | 手动管理 |
| 构建 | `cargo` 一条命令 | 需自配 CMake + SDK |
| 开源可编译性 | 别人 `cargo build` 即可 | 要说明工具链细节 |
| 产物体积 | 约 1–3 MB | 约 200 KB–1 MB |

体积差异对 852 GB 空闲磁盘无意义，因此取 Rust 的安全性收益。

**为什么用 GNU target 而不是 MSVC**：本机没有 MSVC 工具链（无 `cl.exe` /
`link.exe`），但已有 `E:\code_tools\mingw64`（GCC 16.2.0）。用
`x86_64-pc-windows-gnu` 可以直接复用现成 MinGW 链接，省掉约 5 GB 的
VS Build Tools 安装。

## ADR-002：不抢 5300 端口，改为「游戏发给 relay，relay 再扇出」

**结论**：游戏「数据输出IP端口」设为 **5301**；relay 独占 5301，转发给
飞智（5300）与 HUD（5302）。

**背景**：飞智空间站的八爪鱼5 自适应扳机模块独占监听 `127.0.0.1:5300`。

**实测证据**：

1. 启动 `E:\Flydigi Space Station\mods\forza_trigger\ForzaDualSense.exe` 后
   `netstat -ano -p UDP` 显示该进程绑定 `127.0.0.1:5300`（另有临时端口用于与
   `SpaceStationService` 通信，后者常驻监听 `0.0.0.0:7878`）。
2. `ForzaDualSense.dll` 内含 UTF-16 字符串 `5300`。
3. `AdapterTrigger.dll` 含 `IsRaceOn` / `TimestampMS` / `DataOut` /
   `registerDataOutput` / `FORZA_DATA_OUT_PORT` / `DEFAULT_PORT` /
   `TrySetPortNumber` / `FH7_PACKET_LENGTH` / `IsSledFormat` / `IsDashFormat`。
4. `mods/forza_trigger/config/config.default.json` 里**只有扳机动作规则**
   （换挡、刹车、失去抓地力…），**没有任何端口配置项** → 端口对用户不可配置。

**Windows UDP 端口共享语义（本机实测，Windows 10 19045）**：

| 场景 | 结果 |
|---|---|
| 两个套接字都设 `SO_REUSEADDR`，绑同一 `127.0.0.1:port` | **都能 bind 成功**，但单播包**只投递给第一个绑定者**，第二个收不到 |
| socket1 设 `SO_REUSEADDR`、socket2 不设 | socket2 **bind 直接失败**（`通常每个套接字地址只允许使用一次`） |
| 两个都不设 | 第二个 bind 失败 |

**推论**：在 Windows 上**不可能**靠 `SO_REUSEADDR` 让多个进程各自独立地收到
同一份 UDP 单播数据。**必须显式转发。**

**为什么不让 relay 直接占 5300**：占了会把飞智顶掉（先绑者得包），
自适应扳机就废了。而**游戏内的 IP 和端口都可以自由填写**，5300 只是飞智
推荐的取值 —— 所以绕开的成本为零：

```
FH6 ──Data Out──► 127.0.0.1:5301  (relay 独占)
                       │
         ┌─────────────┴─────────────┐
         ▼                           ▼
  127.0.0.1:5300                127.0.0.1:5302
  飞智 ForzaDualSense              fh6-hud
```

用户只需改游戏里一个数字，飞智完全无感。

**顺带好处**：天然支持任意多个消费者（SimHub、录数据脚本…），
参考实现只能硬编码转发给一个固定目标。

## ADR-003：5301 而不是 5300 附近的其他端口

**结论**：relay 默认监听 **5301**。

**理由**：官方 FH6 文档有一条特别提醒：

> `Avoid ports 5200 through 5300, as the game binds its own outgoing socket to a port in this range.`

游戏自己的发送套接字会占用 5200–5300 区间。5301 刚好在该区间之外，
避免与游戏自身冲突。

## ADR-004：解析层用显式逐字段 `from_le_bytes`，不做零拷贝转型

**结论**：不把 `&[u8; 324]` 用 `unsafe` 转成 `&RawPacket`，而是逐字段读取。

**理由**：

1. **对齐**：UDP 接收缓冲区不保证 4 字节对齐，未对齐读取 `f32` 在部分架构是 UB。
   x86 虽然容忍，但没有必要冒这个险。
2. **字节序**：必须小端。x86 恰好是小端所以"能用"，但这是隐式假设，
   换平台或换编译器优化就会出问题。
3. **成本可忽略**：60 Hz × 324 字节，解析开销远低于渲染。

收益是 `#![forbid(unsafe_code)]` 覆盖整个 `fh6-core`。

**同时**保留 `#[repr(C)] RawPacket` 作为**布局的独立交叉验证**：
测试断言 `size_of::<RawPacket>() == 324`，任何偏移量写错都会与结构体顺序矛盾。

## ADR-005：工程按「纯逻辑库 + 薄二进制」拆 crate

**结论**：`fh6-core`（纯逻辑，无 I/O 无 GUI）、`fh6-relay`（lib + bin）、
`fh6-hud`（bin）。

**理由**：参考实现（093_Drift_HUD）把渲染、业务状态机、遥测解析全部塞进一个
**5115 行的 PyQt 类**（125 个方法共享 60 多个可变状态字段），导致
**业务逻辑完全无法单元测试**。

拆开后的直接收益在本项目已经体现：`fh6-core` 与 `fh6-relay` 共
**47 个测试**，全部在**不启动窗口、不连接游戏**的情况下运行，
整轮不到 1 秒。

## ADR-006：relay 拒绝 `SO_REUSEADDR`，端口被占时明确报错

**结论**：`Relay::bind` 不加 `SO_REUSEADDR`，绑定失败直接返回错误。

**理由**：如果允许共享，会出现「bind 成功但收不到包」的静默失败 ——
用户会以为"游戏没发包"，排查成本极高。明确报错并提示用
`netstat -ano -p UDP | findstr :<port>` 查看占用者，体验好得多。

对应测试：`绑定被占用的端口应明确失败而不是静默成功`。

## ADR-007：relay 收到 ICMP 端口不可达时不能退出

**结论**：`pump_once` 把 `ConnectionReset` / `ConnectionRefused` /
`Interrupted` 视为可忽略的瞬时错误。

**理由**：Windows 上 UDP 套接字收到 ICMP 端口不可达后，下一次 `recv_from`
会返回 `WSAECONNRESET`。当某个转发目标暂时没在监听（这是常见情况：HUD 还没
启动、或飞智没开），这是**预期行为**。若不忽略，游戏一发第一个包 relay 就死。

对应测试：`目标端口无人监听时不应崩溃且继续转发给其他目标`。

## ADR-008：HUD 必须做点击穿透

**结论**：HUD 窗口加 `WS_EX_TRANSPARENT`。

**理由**：参考实现只设了
`WA_TranslucentBackground + FramelessWindowHint + WindowStaysOnTopHint + WindowType.Tool`，
**没有做点击穿透**，而且窗口 geometry 被设成**整屏**（以便任意摆放部件）。
结果是鼠标事件被全屏叠加层吃掉，会挡住游戏操作。

本项目作为**待实现的修正项**记录在此（渲染层尚未完成）。

---

## ADR-009：收包与渲染分线程

**结论**：UDP 接收放在独立线程，渲染线程只读最新快照。

**理由**：参考实现把 UDP 轮询、全部业务逻辑、全部渲染挤在 Qt 主线程，
16 ms 的 tick 内要排空 socket 并解析；一旦渲染超时或遇到 GC 停顿就会
**丢遥测包**（UDP 无重传，丢了永久丢）。Rust 侧用线程把收包独立出来，
即使渲染卡顿也不会丢包。

## ADR-010：横向 G 的符号约定定为「右转为正」

**结论**：`g_lateral = (ax*fz - az*fx) / g`，**正 = 右转，负 = 左转**。

**背景**：这个符号在本项目实现过程中**被单元测试抓错过一次**。第一次写成
`az*fx - ax*fz`，测试报出「右转得到 -1G」。

**定案依据（代数，不靠直觉）**：

```
车沿 +Z 前进 → 前进单位矢量 fx = 0, fz = 1
纯转弯时加速度沿 ±X 方向
g_lat = (ax*fz - az*fx)/g = ax/g

约定：右转为正（ISO 8855 车体坐标系，绕 Y 轴正向旋转为右转）
右转 → 向心加速度指向 +X → ax > 0 → g_lat > 0 ✔
```

反面写法得到的是「离心方向」的符号，物理上互为反号。

对应测试：`横向G符号约定为右转正`（含左右对称性检查）。

## ADR-011：渲染层自己光栅化，不用 GDI 落笔

**结论**：所有绘制原语（线、多边形、圆、矩形、文字）都由本项目自己实现
（`crates/fh6-hud/src/raster.rs`），按**预乘 alpha** 直接写画布内存。
GDI 只保留两个用途：创建 DIB 内存画布、以及为文字生成 alpha 掩码。

**背景与实测证据**（本机 Windows 10 19045，画布 400×300）：

```text
2) MoveToEx=1 LineTo=1 GdiFlush=1        → 画线后不透明像素 = 0
3) Rectangle=1                            → 画矩形边框后不透明像素 = 0
4) Ellipse=1                              → 填充椭圆后不透明像素 = 0
5) Polygon=1                              → 填充多边形后不透明像素 = 0
6) CreateFontW=0x3e0a0925 TextOutW=1      → 画文字后不透明像素 = 0
7) Rectangle 填满整屏                      → 不透明像素 = 0
   采样像素 (0,0) = Bgra { b: 0, g: 0, r: 255, a: 0 }
                                             ^^^^^^^^^ alpha 恒为 0
8) 直接写内存 fill_rect                   → 不透明像素 = 120000  ✔
```

**根因**：GDI 会正确写入 RGB 通道，但**从不写 alpha 通道**（留 0）。
分层窗口（`WS_EX_LAYERED` + `UpdateLayeredWindow`）按**每像素 alpha** 合成，
alpha=0 即完全透明 —— 于是 **GDI 画的一切在屏幕上都是不可见的**。

这不是配置问题，而是 GDI 位图模型本身没有 alpha 概念
（它诞生于用 `BitBlt` 做掩码透明的年代）。所有 API 都返回成功（非 0），
所以失败是**静默的** —— 这也是它难排查的原因。

**因此**：

* 绘制原语自己实现，唯一的落笔点是 `Rasterizer::blend_pixel`，
  用标准的预乘 source-over 公式；
* 顺带**彻底去掉了 gdi32 依赖**（只剩 user32 的窗口与消息），产物体积更小；
* 换来真正可控的半透明：面板底衬、辉光、扫描线、网点都能精确设定 alpha。

**文字的例外处理**：GDI 仍是唯一现成的字形光栅化器（自带字体回退、
抗锯齿、CJK 支持），自己实现字体引擎代价过高。折中做法：

1. 用 GDI 在一张**独立小位图**上把文字画成纯白；
2. 读回像素，取 `max(R,G,B)` 作为**覆盖率**（`textmask.rs`）；
3. 用该覆盖率把目标颜色混合进主画布。

中间结果不进入最终画布，因此没有白字残影；颜色与透明度完全可控，
抗锯齿质量来自 GDI。掩码按「文本 + 字号 + 粗细」缓存（上限 512 条）。

## ADR-012：渲染层拆出可测的几何层（`gauge`）

**结论**：`crates/fh6-hud/src/gauge.rs` 只做纯数学与纯数据（角度→坐标、
弧线折线采样、G 值映射、轨迹环缓冲、脏区包围盒、配色），
不含任何绘制调用，因此有 46 个单元测试。

**理由**：渲染层的正确性标准是「看起来对不对」，无法靠断言验证。
但其中**一半是可测的纯数学**：坐标换算写错会让仪表画到屏幕外，
角度约定写反会让指针左右颠倒 —— 这些都能用断言钉死。

**实际收益**：开发过程中 `弧线折线点数与端点正确` 这条测试就抓到了
我自己写错的断言（把仪表 0° 的中点当成「圆心下方」，实际应为「正上方」），
从而确认了「0° 在正上方、-90° 正左、+90° 正右」的约定被正确实现。

**另外**：`--selftest` 把同一套绘制代码跑在内存画布上并写成 BMP，
使渲染结果可以在**不创建窗口、不占用 GPU、不连游戏**的前提下核对。
这是本层唯一的"验收手段"，比盯着一个全屏窗口调试可靠得多。

## ADR-013：中文标签必须放大行距，不能复用英文的行高

**结论**：把字形高度与行距做成**跟语言相关的系数**
（`Labels::glyph_factor()` = 中文 1.28、`Labels::line_factor()` = 中文 1.50），
而不是写死一套行高。

**问题**：最初所有标签都是英文硬编码。改成中文后，同一套排版立刻塌了 ——
截图里中文标签压在下方的数值条上，状态栏六行互相重叠。

**原因（可量化）**：

| | 拉丁大写字母 | 汉字 |
|---|---|---|
| 占字号的比 | 约 0.72（cap height，无降部） | 约 1.00（占满字身框） |
| 行内需要的高度 | 字号 × 1.35 够用 | 字号 × 1.55 才不挤 |

原先的行高按「字号 × 1.35」标定 —— 对英文刚好，对中文差了约 20%。
而**中文并不是「更长的英文」**：它更**高**，也更**方**，同样的行距必然相撞。

**为什么不在 `fh6-core` 里改**：`label()` 返回英文是**数据层的事实**
（有测试断言 `GRIP` 之类的值），翻译属于**呈现层**的选择。因此：

* `fh6-core` 保持原样，`label()` 仍是英文（英文模式下直接复用它）；
* 新增 `fh6-hud/src/i18n.rs`，只做「枚举 → 显示文本」的映射；
* 翻译表的**穷尽性由编译器保证**：`match` 覆盖所有枚举变体，将来给
  `DriftState` 加一个变体，编译就会报错，不会漏翻。

**验收方式（可执行的，不是「看着还行」）**：`i18n.rs` 里有一条测试
`中文模式下不得残留英文名词` —— 遍历所有文案，断言每条要么含中日韩字符，
要么属于允许保留的单位（`km/h`、`G`）。这条测试就是「对中文用户友好」
这个需求的**定义**，将来新增条目忘了翻译会立刻失败。

**顺带修正的布局**：中文面板变高后，三个面板的默认纵向位置从
`40 / 220 / 400` 调整为 `40 / 250 / 470`，行间隙从 `6.0` 收紧到 `4.0`（再乘语言系数）。
